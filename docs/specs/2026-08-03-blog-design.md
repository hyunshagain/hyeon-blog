# 설계 기록 — 자동 발행 경로가 없는 아카이브

작성일: 2026-08-03

## 배경

프로젝트를 끝내면 결과물이 흩어진다. 코드는 저장소에, 분석은 노트북 어딘가에,
"왜 그렇게 결정했는지"는 머릿속에만 남는다. 반년 뒤에 다시 열어보면 코드는 그대로인데
판단의 근거가 사라져 있다.

목표는 프로젝트 결과물과 그때의 판단을 한 곳에 남기는 아카이브를 만드는 것.
목적은 개인 브랜딩 / 포트폴리오다. 트래픽이 아니라 "이 사람이 뭘 할 줄 아는지"가 남는 것.

수집과 정리는 자동화할 가치가 있다. 문제는 어디까지 자동화하느냐다.

## 판단

### 1. 자동으로 채워진 아카이브는 신뢰할 수 없다

LLM으로 초안을 생성해 그대로 쌓으면 편수는 빠르게 늘어난다. 하지만 반년 뒤에 그 기록이
내 판단인지 모델이 만든 문장인지 구분할 수 없게 된다. 아카이브의 가치는 양이 아니라
나중에 그것을 믿을 수 있느냐에 있다.

### 2. 포트폴리오 목적에서는 오히려 마이너스다

읽는 사람이 기계가 쓴 글이라는 걸 알아채는 순간 신호가 0이 아니라 음수가 된다.
자기 생각이 없거나 없는 걸 있는 척한다는 뜻이 되기 때문이다. 편수가 많을수록 더 확실해진다.

두 판단이 같은 처방으로 수렴한다. **AI를 작성자에서 조사원으로 강등시킨다.**

## 결정

### 플랫폼: 정적 사이트 (Astro) + GitHub + Vercel

검토한 대안:

| 안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| **A. Astro + GitHub + Vercel** | git 이력이 곧 검수 기록. 아카이브가 파일로 남아 이식 가능. 저장소 자체가 포트폴리오 | — 채택 |
| B. 자가호스팅 WordPress | 익숙한 편집 경험 | 유지보수 부담. 글이 DB에 갇혀 이력 추적이 안 됨 |
| C. 노션 / 티스토리 등 호스팅 플랫폼 | 설정이 거의 없음 | 통제권이 남의 손에. PR 기반 검수 게이트를 걸 수 없음 |

C가 탈락한 이유가 결정적이다. 이 설계의 핵심은 검수를 사람의 의지가 아니라 배관으로
만드는 것인데, 호스팅 플랫폼에는 그 배관을 놓을 자리가 없다.

프레임워크는 Astro. 콘텐츠 사이트 전용 설계라 Markdown 파이프라인·RSS·이미지 최적화가
기본 제공되고, 기본 출력이 JS 없는 정적 HTML이다. 인터랙티브 데모가 필요한 자리에만
React 아일랜드를 박는다.

### 언어: 한국어 원본 + 영어 번역

영어판은 번역이지 독립 발행물이 아니다. **영어 단독 발행을 구조적으로 막는다** —
`en/<slug>`가 존재하려면 `ko/<slug>`가 있고 발행 상태여야 한다.

이 제약이 없으면 AI가 영어판을 자동으로 불려나가는 그림자 사이트가 생기고,
그게 정확히 splog 패턴이다.

번역 자체는 AI가 해도 된다. 내 문장을 옮기는 것이지 의견을 만드는 게 아니기 때문이다.
단 같은 PR 게이트를 통과해야 한다.

### 콘텐츠 모델: 경로가 곧 메타데이터

`posts/<lang>/<pairKey>.md`. `lang`과 짝 키를 프런트매터에 중복하지 않으므로 어긋날 수 없다.

`evidence`(고유 증거)는 Zod 스키마에서 최소 1개를 강제한다. 없으면 빌드 자체가 실패한다.
이 필드의 진짜 기능은 검증이 아니라 질문이다. 채우는 순간 "이 글에 내가 낸 게 뭐지"를
강제로 묻게 된다.

### 검수를 의지가 아니라 배관으로

지난번 실패 지점은 "검토하겠다는 의지"였다. 매번 읽겠다고 생각해도 큐가 쌓이면 읽지 않게 되고,
하필 바쁠 때 가장 많이 쌓인다.

그래서 이 저장소에는 자동 발행 경로가 없다. `main`은 보호되고, 글은 PR로만 들어오며,
PR은 게이트 8종을 통과해야 머지된다. 머지가 곧 발행이고 머지는 사람만 한다.

### 게이트 8종

세부는 README 참조. 설계상 주목할 점 두 가지.

**4번(H2 골격 유사도)이 실질적으로 가장 많이 걸린다.** LLM 초안은 제목만 바뀌고 뼈대가
매번 같다. 사람은 잘 눈치채지 못하지만 자카드 유사도로 재면 숫자로 나온다.

**8번(발행 속도)만 경고다.** 차단이 아니다. 규칙이 상황을 이기면 우회하게 되고,
한 번 우회하면 나머지 일곱 개도 권위를 잃는다. 막아야 할 것과 알려주면 될 것의 구분이
이 시스템에서 가장 어려운 판단이었다.

## OpenClaw 연동

다른 머신에서 돌고 있는 OpenClaw가 파이프라인을 돌린다. 경계는 하나다: **머지는 사람이 한다.**

에이전트가 담당하는 것 — 글감 제안, 리서치 노트, 초안 골격, PR 생성, 리뷰 코멘트,
게이트 실패 알림, 링크 검사, 배포 감시, 번역 초안.

에이전트가 하지 않는 것 — `main` push, PR 머지, 본문 작성, `draft: false` 전환,
게이트 스크립트 수정.

### 두 겹의 방어

**권한**: fine-grained PAT에서 `Administration`을 뺀다. 규칙을 지키는 것과 규칙을 바꿀 수
없는 것은 다르다.

**경로 격리**: 에이전트가 웹에서 가져온 텍스트는 `content/_research/`에만 쓴다.
이 디렉토리는 `src/` 밖이라 Astro가 읽지 않는다. 프롬프트 인젝션이 성공해도 리서치 노트까지가
끝이고, 그 노트는 PR diff에 그대로 드러난다.

OpenClaw는 shell·브라우저·메시징 접근을 모두 가진 에이전트라 공격면이 넓다.
2026년에 CVE-2026-25253(게이트웨이 장악), 링크 프리뷰를 통한 데이터 유출, 스킬 디렉토리
악성 스킬, 자격증명 유출 사례가 보고됐다. 운영 수칙은 `openclaw/RULES.md`에 정리했다.

## 알려진 한계

- `evidence` 검사는 파일 존재만 확인한다. 아무 파일이나 가리키면 통과한다.
- 상투어 목록은 유한하다. 목록에 없는 새 상투어는 잡히지 않는다.
- 분석 블록은 글자 수만 센다. 내용의 질은 보지 못한다.

이 검사들이 막으려는 건 결심한 우회가 아니라 귀찮아서 대충 넘어가는 나 자신이다.
우회 비용이 제대로 쓰는 비용보다 크기만 하면 대부분의 날에는 제대로 쓰게 된다.

완전 차단이 필요해지면 OpenClaw용 **별도 머신 계정**을 만들고 "승인 1건 필수"를 건다.
GitHub이 자기 PR 자기 승인을 막으므로 그때는 기술적으로 완전해진다. 1인 블로그에는 과하다고 보고
현재는 채택하지 않았다.

## 남은 설정 (계정 작업)

1. GitHub 저장소 생성 후 이 디렉토리를 push
2. CI를 한 번 실행 (status check 이름이 생겨야 3번에서 선택할 수 있다)
3. `main` ruleset 설정
   - Require a pull request before merging (approvals 0 — 1인 저장소라 자기 승인이 안 됨)
   - Require status checks to pass → `품질 게이트`
   - Block force pushes
   - Bypass list는 비워둔다. 자기 자신을 넣으면 게이트의 의미가 없다
   - ⚠️ GitHub Free에서 ruleset은 **public 저장소에서만** 강제된다. private은 Pro 이상 필요
4. Vercel에 저장소 연결 (Astro 자동 감지, 어댑터 불필요)
5. `astro.config.mjs`의 `site`를 실제 도메인으로 교체
6. OpenClaw용 fine-grained PAT 발급 → `openclaw/RULES.md`의 권한 표대로
7. 그 머신에 `openclaw/HEARTBEAT.md`, `openclaw/RULES.md` 연결
